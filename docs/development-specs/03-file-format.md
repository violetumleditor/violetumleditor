# 03 — File format and persistence

This document is the **compatibility contract**: every file the current application can read must be readable by the target, and every file written by the target must be readable by the current application for as long as coexistence is needed.

Evidence level: [V] = observed in the code; [D] = deduced; [?] = to confirm by generating a corpus.

## 1. Principles

1. **The format is a self-contained HTML file** that contains:
   - a **PNG thumbnail** of the diagram (base64), displayable directly in a browser;
   - the **diagram itself**, as XML, inside a `<SCRIPT id="content">` block;
   - a **viewer page** (CSS, JavaScript, header) that lets the user inspect the XML and open the diagram in the online editor (section 6).
2. **Extensions** depend on the diagram type: `.class.violet.html`, `.seq.violet.html`, `.activity.violet.html`, `.state.violet.html`, `.object.violet.html`, `.ucase.violet.html` [V, `copilot-instructions` and the `getFileExtension` of the plugins].
3. **The XML is generated by reflection** on the Java fields: element and attribute names are the names of classes and fields. **The Java code is therefore the schema**: any renaming of a field or class breaks existing files, unless a compatibility mapping is added (section 5).
4. **There is no format version number** in the file. The application version only appears in the viewer page (`${version}`). Compatibility therefore relies on the presence of known tags [V].

## 2. HTML container

### 2.1 Template `XHTMLFileTemplate.violet.html` [V]

A 282-line file starting with a UTF-8 byte order mark (BOM). It contains three markers replaced when writing:

| Marker | Replaced by | Where |
|---|---|---|
| `${version}` | Application version (`app.version.number`) | Subtitle "Generated with Violet UML Editor version …" and the `sourceVersion` property of the JavaScript |
| `${image}` | `data:image/png;base64,…` | `<IMG id="diagramPreview" src="…">` tag |
| `${content}` | XML of the diagram | `<SCRIPT id="content" class="source" type="text/xml"><![CDATA[…]]></SCRIPT>` |

### 2.2 Simplified page structure

```
<HTML>
 <HEAD>  meta (description, keywords, charset UTF-8, viewport), <TITLE>Violet UML Diagram
         <STYLE>  embedded stylesheet (CSS variables, light theme)
         <SCRIPT type="text/javascript">  page functions (see 2.3)
 <BODY>
   <DIV class="wrapper">
     <DIV class="header"> title, subtitle (version), action buttons
     <IMG id="diagramPreview" src="data:image/png;base64,…">
     <SCRIPT id="content" type="text/xml"><![CDATA[ …XML… ]]></SCRIPT>
 </BODY>
</HTML>
```

Note: the `<SCRIPT id="content">` tag is **the anchor point** for reading. A target that reads these files must find this block, whatever the formatting of the page around it.

### 2.3 JavaScript functions of the page [V]

| Function | Role |
|---|---|
| `switchVisibility()` | Shows or hides the XML block ("Toggle Embedded Source" button) |
| `getSuggestedFilename()` | Derives a file name from the URL, defaulting to `diagram.violet.html` |
| `encodeBase64Utf8(text)` | UTF-8 then Base64 encoding, in chunks of 32 KB |
| `openInOnlineEditor()` | Opens the online editor and sends it the diagram ("Open In Online Editor" button) |

## 3. XML content

### 3.1 Root and general structure [V]

The root is the **graph class name with a lower-case initial**: `classDiagramGraph`, `sequenceDiagramGraph`, etc. It contains, in the order of the declared fields of `AbstractGraph` and then of the subclasses:

```
<classDiagramGraph>
  <nodes> … one element per node … </nodes>
  <edges> … one element per edge … </edges>
  <resources> … images, one per unique image … </resources>   (only if there are images)
</classDiagramGraph>
```

### 3.2 Serialisation rules [V]

Derived from the `XMLPersistenceService` writer (1,098 lines). They apply recursively.

| # | Case | Written form | Example |
|---|---|---|---|
| R1 | Element name | Name of the **field** for a property; name of the **class** (lower-case initial) for an object inside a collection | `<name>`, `<classNode>` |
| R2 | `static`, `transient` or synthetic field | **Ignored** | (`toolTip`, `graph`, `z`) |
| R3 | `parent` field | **Ignored** (avoids cycles) | — |
| R4 | `value` field of type `String` | Written as an **attribute** of the parent element | `<id value="…"/>` |
| R5 | `null` value | **Omitted** | — |
| R6 | Empty `children` collection | **Omitted** | — |
| R7 | `preferredSize` null (0×0) | **Omitted** | — |
| R8 | Empty `cropInsets` | **Omitted** | — |
| R9 | `Point2D` named `location` | Compact form | `<location x="40.0" y="20.0"/>` |
| R10 | `Point2D` with another name | Element with `x` and `y` | `<startLocation x="…" y="…"/>` [D, exact form to confirm] |
| R11 | `Rectangle2D` named `preferredSize` | `width` and `height` attributes | `<preferredSize width="288.97" height="577.94"/>` |
| R12 | `Color` | `red`, `green`, `blue`, `alpha` attributes | `<backgroundColor red="255" green="255" blue="255" alpha="255"/>` |
| R13 | Java enum | `name` attribute | `<endArrowHead name="TRIANGLE"/>` [D] |
| R14 | `SerializableEnumeration` (styles, arrowheads) | `name` attribute (serialisable name) | `<bentStyle name="HV"/>` [D] |
| R15 | Simple type (text, number, boolean) | Element containing the escaped text | `<revision>0</revision>` |
| R16 | Text | XML escaping: `& < > " '` | `&lt;html&gt;` |
| R17 | Collection | Container element, one child per item; child tag = class name | `<children>…<classNode>…</classNode></children>` |
| R18 | Array | Same principle as R17 | `<transitionPoints>…</transitionPoints>` |
| R19 | **First** occurrence of a node | Full serialisation | `<nodes><classNode>…</classNode></nodes>` |
| R20 | **Subsequent** occurrences of a node (e.g. edge end) | Reference by identifier | `<startNode id="uuid"/>` |
| R21 | `BufferedImage` image | Reference by identifier in `<resources>` | `<image id="…"/>` then `<resources><image id="…">base64</image></resources>` |
| R22 | String containing `<html>` | Interpreted as HTML at display time (see 02, section 4.4) | — |

> **Point of attention [V]:** the reference identifiers (R20) are those of the nodes (`Id`). Since `AbstractGraph.addNode` reassigns a new `Id` on every insertion (see 02, 2.1), the **stability of identifiers between two saves** depends on the sequence of operations. References remain consistent **within a file**, because they are computed when writing.

### 3.3 Order of elements [V]

Fields are written **in Java declaration order**, superclass first (`collectSerializableFields` walks the hierarchy from `Object`). **The order is part of the format**: reordering fields changes the files produced, without making them unreadable for the reader (which finds fields by name). For the target, order is therefore not a functional requirement, but it makes file comparisons easier during the migration.

### 3.4 Illustrative example

> **Example reconstructed from rules R1 to R21.** It was **not** produced by running the code. The exact names of the sub-elements of `MultiLineString` and the fields of `Id` must be validated by generating the corpus (document 06, phase 0).

```xml
<classDiagramGraph>
  <nodes>
    <classNode>
      <id value="3f2a9c1e-5b7d-4e0a-9d11-2c8f6a7b4e10"/>
      <location x="220.0" y="120.0"/>
      <revision>0</revision>
      <borderWidth>1</borderWidth>
      <name>
        <text>Car</text>
      </name>
      <attributes>
        <text>registrationNumber : String</text>
      </attributes>
      <methods>
        <text>start()</text>
      </methods>
    </classNode>
    <classNode>
      <id value="9d0e4b7a-1c2f-4a6e-8b3d-7e5f0a9c2d11"/>
      <location x="40.0" y="20.0"/>
      <name><text>Driver</text></name>
    </classNode>
  </nodes>
  <edges>
    <associationEdge>
      <id value="c4b1f2e9-0a3d-4c7b-9e6f-5d8a1b2c3e44"/>
      <startNode id="9d0e4b7a-1c2f-4a6e-8b3d-7e5f0a9c2d11"/>
      <endNode id="3f2a9c1e-5b7d-4e0a-9d11-2c8f6a7b4e10"/>
      <startLocation x="40.0" y="20.0"/>
      <endLocation x="40.0" y="20.0"/>
      <transitionPoints>
        <edgeTransitionPoint x="120.0" y="70.0"/>
      </transitionPoints>
      <backgroundColor red="255" green="255" blue="255" alpha="255"/>
      <endArrowHead name="TRIANGLE"/>
    </associationEdge>
  </edges>

```

What the example shows, and what must be verified on the corpus:
- the **reference** `<startNode id="…"/>` points to a node already written in `<nodes>` (R20);
- the **tag names** of edges and transition points are derived from class and type names (`associationEdge`, `edgeTransitionPoint`) [D];
- the **styles** (`bentStyle`, `lineStyle`, arrowheads) appear only if their value is not null [D].

## 4. Reading

### 4.1 Reading chain [V]

1. `XHTMLPersistenceService.read` reads **the whole stream** as bytes (reading one byte at a time, through a `BufferedInputStream`).
2. XML extraction with a regular expression:
   ```
   <script[^>]+id=["']content["'][^>]*>\s*<!\[CDATA\[(.*?)]]>\s*</script>   (DOTALL, case-insensitive)
   ```
   If the expression does not match: error "Invalid XHTML file format: missing CDATA section".
3. The extracted XML is read by `XMLPersistenceService.read`, which parses it with a **hardened** DOM:
   - `FEATURE_SECURE_PROCESSING` enabled;
   - `disallow-doctype-decl` enabled (no DTD, hence no external entities);
   - `setXIncludeAware(false)`, `setExpandEntityReferences(false)`.
4. Images in `<resources>` are **preloaded** before the nodes are read (`preloadResources`).
5. References (`id=…`) are resolved through an identifier table (`idMap`, `imageIdMap`).
6. Each node receives its graph (`aNode.setGraph(graph)`) after the complete read.

### 4.2 Forms read but not produced

Older files use other forms, recognised by the reader:

| Form | Example | Source |
|---|---|---|
| Short class name for nodes | `<classNode/>` instead of a full node | Sample files of the `violetproduct-swing` module [V] |
| Plural container tags | `<nodes>`, `<edges>` | Idem |
| 0.16 class names (`com.horstmann.violet.ClassNode`, etc.) | Mapping by `Violet016FileFilterExtensionPoint` | 7 entries in `Violet016BackportFormatService` + plugin tables [V] |

### 4.3 History: XStream, then a home-made reader [V/D]

- The code **no longer imports XStream** [V], although the documentation cites it as the main persistence layer.
- Test names (`shouldReadLegacyXhtmlSamplesWithoutXStream`, `shouldReadProvidedLegacyXstreamFile`, `LegacyXmlWriteCompatibilityTest`) indicate that the current format is a **"legacy" format reproduced by hand** to stay compatible with files written by XStream [D].
- A service `StandardJavaFilePersistenceService` uses `java.beans.XMLEncoder` / `XMLDecoder`, but is **instantiated nowhere** [V]: it is a potentially abandoned format.
- The service `JSONPersistenceService` has a misleading name: it wraps the XML inside JSON (`{"xml": …}`) and is only used by its test [V].

### 4.4 Expected compatibility (matrix)

| Source | Reading required | Writing required |
|---|---|---|
| Current `.violet.html` file (this format) | **Yes** | **Yes** |
| `.violet.html` file written by XStream (older versions) | **Yes** (example provided: `sample.class.violet.html`) | No |
| 0.16 file (`com.horstmann.violet.*`) | **Yes** (mapping) | No |
| Bare XML (no HTML wrapper, `XMLPersistenceService` stream) | Yes (same reader) | Yes (used internally, copy/paste) |
| `java.beans` XMLEncoder format | Not produced; **reading not required** [D] | No |
| JSON (`{"xml": …}`) | Not used in production | No |

## 5. Compatibility mechanisms

| Mechanism | Scope | File |
|---|---|---|
| 0.16 class name table | 7 entries, including `BentStyle`, `LineStyle`, `ArrowHead`, `DiagramLinkNode`, `NoteEdge`, `NoteNode`, `PointNode` | `Violet016BackportFormatService` |
| Per-plugin name table | `getMappingToKeepViolet016Compatibility()` (e.g. `ClassDiagramPlugin`) | Each plugin |
| Class of old names marked for deletion | File named `FileCompatiliblyServiceToDelete` | `violetplugin-classdiagram` [V] |
| Write non-regression tests | Check the exact form: `<location x=`, `<backgroundColor red=`, absence of `class=` attribute, absence of `reference=` for colours, `<resources>` present | `LegacyXmlWriteCompatibilityTest` [V] |
| Read tests | Read `sample.*.violet.html` (6 types) | `LegacyXhtmlCompatibilityTest` [V] |

> **Reference value to keep [V]:** the width `288.9729729729727` and height `577.9459459459454` in the write test illustrate the precision of floating-point values. A target that rounds differently will produce files that fail this test. A **tolerance** must be decided (see 07).

## 6. Online editor and diagram transfer

The "Open In Online Editor" button of each file opens `https://violetumleditor.github.io/product` [V]. Observed protocol:

1. `window.open(URL, "_blank")`; if the window is blocked, an alert "Popup blocked".
2. Listens for `message` events with an acknowledgement type `violet-import-ack`.
3. Every 250 ms, up to 40 attempts (10 s), sends the editor a message:
   ```json
   { "type": "violet-import-v1:", "payload": {
       "filename": "<name derived from the URL>",
       "sourceVersion": "<version>",
       "xmlContent": "<XML of the diagram>",
       "htmlContent": "<complete HTML document>" } }
   ```
   sent with `targetOrigin = https://violetumleditor.github.io`.
4. **Fallback:** the same payload, encoded in UTF-8 Base64 and prefixed by `violet-import-v1:`, is placed in **`window.name`** of the opened window.

### Security analysis of the protocol [V/D]

| Point | Finding | Level |
|---|---|---|
| Target origin | `targetOrigin` fixed to the expected origin ✔ | Good |
| Acknowledgement check | Checks `event.source === editorWindow` and the type ✔; **no check of `event.origin`** | Acceptable [D] |
| Data sent | The **entire HTML document** (thumbnail, XML, script) goes to an external site | To be documented for the user |
| `window.name` fallback | The data remains readable in `window.name` while the tab is open, and is exposed to any page later navigated to in that window [D] | **Risk to assess** |
| Hard-coded URL | `https://violetumleditor.github.io/product` embedded in the template | External dependency; hosting migration needed if the editor moves |

> **Decision for the target:** keep this transfer (a visible feature), replace it with a stricter mechanism, or remove it. In every case, the generated file contains the whole diagram, and this behaviour must be **documented for the user**.

## 7. Writing: steps and costs

1. XML serialisation of the graph (R1 to R21), into an in-memory buffer.
2. **Rendering of the thumbnail**: `FileExportService.getImage(graph)` draws the whole diagram as an image, then `ImageIO` encodes it as PNG and Base64 [V].
3. Replacement of the template markers.
4. UTF-8 write.

> **Consequence [D]:** every save **triggers a complete graphics rendering**. On a large diagram, this is the dominant cost, and it depends on the Java2D drawing engine. The target must either reproduce an equivalent off-screen rendering or accept a thumbnail of different quality. This choice must be made early (document 06).

## 8. Exports other than the `.violet.html` format

| Format | Mechanism | Library | Remark |
|---|---|---|---|
| PNG | `FileExportService` → `ImageIO` | Java2D | Present [V] |
| PDF | `FileExportService.exportToPdf`: `PDFGraphics2D`, PDF version 6, embedded fonts (`EMBED_FONTS=true`), page sized to the diagram | FreeHEP 2.4 | Present [V] |
| Printing | `framework.printer` | `java.awt.print` | Present [V] |
| SVG / JPEG / others | **Not found** in the code | — | Absent [V] |

## 9. Loading security

| Control | Status |
|---|---|
| External XML entities (XXE) | **Protected**: DOCTYPE refused in both parsers |
| HTML parsing | By **regular expression** on the text, not by an HTML parser: a malformed page may be misread [D] |
| File size | **No limit** when reading [V] |
| Active content in the page | The file contains JavaScript. If opened locally, it runs in the browser. The script does not inject diagram content into the DOM without escaping, but this claim has not been tested [?] |

## 10. Edge cases the target's tests must cover

1. Empty file, or file without a `<SCRIPT id="content">` block.
2. XML with a DOCTYPE (must be rejected).
3. Text containing `<html>`, `]]>`, `&`, quotes and characters outside the BMP (emoji).
4. Node referenced by an edge but absent from `<nodes>` (must fail cleanly).
5. Duplicated image (same `BufferedImage`): a single entry in `<resources>`.
6. Diagram with no node and no edge.
7. 0.16 and XStream files provided in `violetproduct-swing/src/test/resources`.
8. Negative coordinates and very large values (floating-point overflow).
9. Colours with partial alpha.
10. Edge whose end node is null (reading must fail, cf. 02, I-2).

## 11. Reference corpus to produce (phase 0)

To validate the points marked [?], a corpus must be **generated** with the current version:

- one file per diagram type, with all node and edge types;
- edge cases (section 10);
- the six existing `sample.*.violet.html` files;
- the **expected outputs**: raw XML, thumbnail PNG, exported PNG and PDF.

This corpus becomes the acceptance test of the migration (see 06 and 07).
